Emulator notes · Game Boy hardware

Inside a cartridge

A byte has no meaning. It is eight lit-or-unlit squares, and nothing more. Meaning is a convention applied by whoever reads it — which is why the same byte 0x02 means “MBC1 with RAM” at one address and “128 KiB” at the next one along.

01

Two numbers that are constantly confused

Almost every early misunderstanding about memory traces back to this one distinction. When 0x0148 and 0x00 appear in the same sentence, they are not the same kind of thing at all:

The address

Where a byte lives. A 16-bit number, 0x0000–0xFFFF, because the Game Boy has 16 address wires. It is not stored anywhere — it is what you put on the wires to select a slot.

Four hex digits. Always.

The contents

What is in that slot. An 8-bit number, 0x00–0xFF, because each slot is eight squares wide. This is the thing that actually exists in silicon.

Two hex digits. Always.

Think of memory as a very long shelf with 65,536 numbered slots, each holding exactly one byte. The slot number is the address; the byte is the contents. Two hex digits means you are looking at contents. Four hex digits means you are looking at a position.

The same shelf, read three ways

Address:   0x0147     ← 4 digits: which slot on the shelf
Contents:    0x00     ← 2 digits: the byte sitting in it
Meaning:  ROM_ONLY     ← what the spec says that byte means HERE

The third line exists only in the documentation. The hardware knows nothing about it.

Why the header is a particularly bad offender. Its fields are one or two bytes each, so a 4-digit address sits next to a 2-digit value on every line, and the eye wants to read them as the same kind of number. They never are. In the hex dump above, the grey column on the left is addresses; everything colourful is contents.
02

The shelf, end to end

All 65,536 slots exist whether or not anything is behind them. Different regions of the shelf are wired to different chips, and the component that routes an address to the right one is the memory bus — the heart of any emulator.

Notice how little of it is the cartridge: the ROM gets 0x0000–0x7FFF, just 32 KiB of the 64 KiB space. Everything above 0x8000 is the console's own hardware.

This is why bank switching exists. A 16-bit address can name 65,536 slots and no more. Pokémon Red is 1 MiB. There is no address you could put on the wires to reach byte 900,000 — so the cartridge cheats: it keeps a register saying “which 16 KiB chunk is currently visible at 0x4000–0x7FFF”, and the game rewrites that register as it runs. The address does not change. What answers to it does. Byte 0x0147 of the header is what declares which chip does the answering.
03

The ROM file and the address space are the same bytes

A .gb file on disk is a plain array of bytes, indexed from zero. The console maps the first 32 KiB of that array directly onto addresses 0x0000–0x7FFF.

rom = Path("tetris.gb").read_bytes()   # 32768 bytes

rom[0x0147]        # file offset 0x0147
bus.read(0x0147)   # memory address 0x0147
                   → the same byte, for a 32 KiB cartridge

So for a ROM-only cartridge, file offset and memory address are numerically identical, and the file can be indexed directly. That is why parsing a header needs nothing but slicing — no bus, no CPU, no emulation at all.

It stops being true the moment a mapper appears. With MBC1, address 0x4000 might be file offset 0x4000, or 0x8000, or 0x3C000 — depending on what the game last wrote to the bank register. Address and offset are only accidentally equal in the simple case, and code that assumes otherwise breaks on the first cartridge larger than 32 KiB.
One way to hold it. The ROM is an array and the address is an index into it — but the memory bus is a function that decides which array, and which index into that array, a given address refers to. For a ROM-only cartridge that function happens to be the identity. For everything else it is not.
04

What happens when you press power, in order

Nothing about this order is arbitrary — each step exists because of the one before it.

Step 6 is the one worth staring at. Before it, addresses 0x0000–0x00FF return the boot ROM's bytes; after it, the exact same addresses return the cartridge's bytes. The cartridge data was there the whole time, hidden underneath:

Before — boot ROM mapped

0x00000x31 boot ROM
0x00010xFE boot ROM
0x0000cartridge byte
0x01000x00 cartridge

PC starts at 0x0000 and runs the console's own code.

After — 0x01 written to 0xFF50

0x0000cartridge byte
0x0001cartridge byte
0x0000boot ROM — gone forever
0x01000x00 cartridge

The boot ROM cannot be mapped back in without a power cycle.

Why the entry point is only four bytes. The boot ROM jumps to 0x0100, but the header starts at 0x0104. That leaves the game exactly four bytes of runway before it would start executing the Nintendo logo as if it were code. So every cartridge puts the same thing there: NOP then JP 0x0150 — one padding byte and a jump over its own metadata. Selecting bytes 0x0100–0x0103 in the dump at the top shows exactly that.

What this means for an emulator

Most emulators skip the boot ROM entirely. Its 256 bytes are a separate copyrighted file that may not be present, and its only lasting effect on the machine is the register state it leaves behind. So a CPU can simply start in the post-boot condition:

RegisterValueWhy that value
A0x01identifies the hardware as DMG
F0xB0flags left over from the checksum routine
BC0x0013leftover
DE0x00D8leftover
HL0x014Dthe address the checksum loop stopped at
SP0xFFFEtop of high RAM — the stack grows down from here
PC0x0100the cartridge entry point

HL = 0x014D is not a coincidence — it is literally where the boot ROM's loop counter finished.

05

A size byte that is not a size

This is the most important idea here. The byte at 0x0148 in the header above is 0x00. The ROM is 32,768 bytes. Those two numbers have nothing to do with each other — because the byte is not the size. It is an index into a rule:

rom_size_bytes = 32768 << value      # 32 KiB, doubled `value` times
bank_count     = 2 << value

A single byte can only count to 255. ROM sizes go up to 8 MiB — 8,388,608 — which does not fit. But sizes are always a power of two, so instead of storing the number, you store how many times to double. Eight megabytes becomes the byte 0x08.

The complete ladder — every legal value of 0x0148

Each bar is twice the one above. The highlighted row is the header shown at the top.

This is the same trick as the place values in a byte, one level up: shifting left by one doubles, so the stored byte is an exponent. It is compression by convention — the spec and the console agree on the rule, so the number never has to be written down.

And now the byte that means three different things

Here is the whole point. Take the byte 0x02. Put it in three consecutive slots:

AddressByteFieldWhat 0x02 means there
0x01470x02Cartridge typeMBC1 + RAM
0x01480x02ROM size128 KiB, 8 banks
0x01490x02RAM size8 KiB, 1 bank

Identical eight squares. Three unrelated meanings. The address is what selects which decoding rule applies — which is why parsing a header amounts to nothing more than a list of “at this offset, apply this rule”.

RAM size makes the point even harder, because it is not a shift and not even a sequence. It is a bare lookup table with a hole in it and two values out of order:

Byte at 0x0149RAMBanks
0x00none—
0x01unused—
0x028 KiB1
0x0332 KiB4
0x04128 KiB16
0x0564 KiB8

0x04 is larger than 0x05. No formula produces that; it is historical accident, frozen into the spec. Which is why a parser needs a literal lookup table for this field and a shift for the one before it — the encoding is a property of the individual field, not of the machine.

06

The header checksum, one step at a time

The algorithm is three lines and depends entirely on 8-bit wraparound — an 8-bit register rolling over like an odometer, doing real work:

checksum = 0
for address in 0x0134 ..= 0x014C:      # title through version, inclusive
    checksum = (checksum - rom[address] - 1) & 0xFF

It starts at zero and immediately goes negative, so the very first step wraps. Here are the opening iterations over the header above, which begin with the title TETRIS:

Every row where the subtraction would go below zero is a wrap — and that is most of them. In a language with fixed-width integers the truncation is free; in one with arbitrary-precision integers, an unmasked running total marches off toward negative infinity and the final comparison never matches.

The inclusive-range trap. The spec says 0x0134 through 0x014C inclusive, which in Python is range(0x0134, 0x014D) — 25 bytes. Stopping one byte early produces a checksum that is wrong for every ROM in existence, which is at least a loud failure rather than a subtle one.
07

One field faces the other way

The global checksum at 0x014E–0x014F is a 16-bit value stored big-endian — high byte first. Everything else on the Game Boy is little-endian.

Global checksum · big-endian

0x014E: 18   ← high byte
0x014F: 41   ← low  byte

value = 0x1841

int.from_bytes(rom[0x014E:0x0150], "big")

Everything else · little-endian

0x0102: 50   ← low  byte
0x0103: 01   ← high byte

value = 0x0150

the jump target in JP 0x0150

Those two cards hold four bytes from the same header, four addresses apart, read in opposite directions. Nothing in the bytes says which is which — the spec does. Same lesson as section 05: meaning lives in the reader, not the data.

An argument for where byte order belongs. If the helper that joins two bytes into a 16-bit value stays ignorant of endianness, this exception costs exactly one "big" at one call site. If that helper bakes in little-endian instead, a system with a single big-endian field now needs two functions and a rule for remembering which fields want which. Byte order is a property of how a value is laid out in an addressable store — so it belongs wherever addresses do, and nowhere else.

When a header field decodes to something absurd, check the two numbers first: an address used where an offset was meant, or two digits read where the field is four, accounts for most of it. Everything above is documented exhaustively in Pan Docs, which remains the reference for all of it.
