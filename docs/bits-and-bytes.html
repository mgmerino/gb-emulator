Emulator notes · Game Boy hardware

Bits, bytes & hex

Everything the Sharp SM83 does is eight squares wide. Once you can read a row of squares three ways at once (as a pattern, as a number, as two hex digits), the rest of the CPU stops being mysterious.

Hex0x00
Unsigned0
Signed0

Watch the hex digits: the left four squares only ever change the left digit, the right four only the right one. That is the whole trick, and section 03 explains why.

01

A bit is a square. A byte is eight of them.

A bit is one square that is either lit or unlit. Nothing else. There is no “value” inside it beyond on and off.

Meaning comes from position. We agree that each square is worth double the one to its right, starting at 1 on the far right. Those are the powers of two:

To read a byte as a number, add up the weights of the lit squares. That is the entire conversion.

Worked example · 165

Eight squares give 28 = 256 distinct patterns, so a byte holds 0 to 255. Zero is one of those patterns, the one with nothing lit.

Why the leftmost square is called bit 7, not bit 1. Bits are numbered by the exponent of their weight: the square worth 2⁰ = 1 is bit 0, and the one worth 2⁷ = 128 is bit 7. So numbering runs right-to-left while reading runs left-to-right. Every hardware document you will read uses this convention, including Pan Docs.
02

Why not just use decimal?

Because decimal digits do not line up with squares. Look at what happens when you flip a single square in the middle of a byte:

Decimal · no relationship

8

24

One square changed. Both digits changed.

Hex · one digit per four squares

0x08

0x18

One square changed. One digit changed.

Hexadecimal is base 16, and 16 = 2⁴. That single fact means one hex digit corresponds to exactly four squares, always, with no carrying between them. Decimal is base 10, and 10 is not a power of two, so a decimal digit maps to nothing in particular.

The 0x prefix is not part of the number. It is just Python (and C, and Ruby) telling you “read what follows as base 16”. 0xFF, 255 and 0b11111111 are three spellings of one value. In Python, 0xFF == 255 is True.

03

The nibble: four squares, sixteen states, one digit

Four squares have 2⁴ = 16 possible patterns. Base 16 has 16 digits. So they map one-to-one, perfectly, with nothing left over. Four bits are called a nibble, half a byte, and yes, that is the real name.

The complete mapping, and the only table here worth memorising:

The letters exist because ten through fifteen need single characters: A=10, B=11, C=12, D=13, E=14, F=15. In a numeric context F is the digit fifteen, and fifteen is what four lit squares add up to (8+4+2+1).

A byte is two nibbles, so it is always exactly two hex digits: the left nibble becomes the left digit, the right nibble the right digit.

0xFF · every square lit

high nibble = 1111 = F
low nibble = 1111 = F

F, F  →  0xFF  =  15 × 16 + 15  =  255

0xA5 · a mixed pattern

1010 = 8+2 = 10 = A
0101 = 4+1 = 5 = 5

A, 5  →  0xA5  =  10 × 16 + 5  =  165

To go from squares to hex: chop into two groups of four, read each group as 0–15, write it as a digit. To go from hex back to squares: expand each digit into its four squares. You never need to think about the whole byte at once.

The practical payoff. When Pan Docs says a register's bit 4 selects the button row, you can see it: bit 4 is the top square of the low nibble, so it is the 1 in 0x1_. Reading 0x10 as “bit 4 set” becomes instant, without arithmetic.
04

Sixteen bits: two bytes, four digits

Addresses on the Game Boy are 16-bit, so the address space runs 0x0000 to 0xFFFF, which is 2¹⁶ = 65,536 locations. Same rules, just a longer row: four nibbles, four hex digits.

0x1234

1
2
3
4

The eight darker squares are the high byte (0x12), the eight lighter ones the low byte (0x34).

Splitting and joining is pure square-shuffling. To get the high byte you shift the row eight places right, dropping the low half off the end. To get the low byte you mask with 0xFF, which is section 05.

This is why register pairs exist. The CPU has 8-bit registers B and C, but instructions can use them together as a 16-bit BC. BC is literally B's eight squares placed to the left of C's eight squares. join_bytes(B, C).
05

Masking is a stencil

AND lights a square in the result only if it is lit in both input rows. Put a row of eight lit squares underneath a wider value, and everything sticking out above gets cut away.

0x1FF & 0xFF → 0xFF

0x01FF · 511
&
0x00FF · the stencil
=
0x00FF · 255

The ninth square had nothing above it in the stencil, so it went dark. 511 became 255. The carry was thrown away, exactly as an 8-bit register would.

This is why & 0xFF is mandatory in Python. In C, a uint8_t is physically eight squares wide and the ninth has nowhere to go. In Python an integer grows as many squares as it needs, forever, so 0xFF + 1 quietly becomes a nine-square number instead of wrapping to zero.

Same in Ruby. Integer is unbounded there too, so this is an emulation quirk rather than a Python one. A C emulator gets the truncation free from the type system; we have to ask for it, on every single arithmetic result that lands in a register.

Setting bit 3 · v | (1 << 3)

1 << 3 builds a row with only bit 3 lit; OR forces that square on and leaves the rest alone.

Clearing bit 3 · v & ~(1 << 3)

~ inverts every square, giving a stencil with a single hole. AND then punches that one square out.

06

Signed values: one square changes its mind

A few instructions (JR, ADD SP,e8) need to jump backwards, so their operand byte has to represent negative numbers. There are no extra squares available. The trick is to reinterpret one that already exists.

In two's complement, the leftmost square keeps its magnitude but flips its sign: instead of being worth +128, it is worth −128. Every other square is unchanged.

Unsigned · 0xFF = 255

128+64+32+16+8+4+2+1 = 255

Signed · 0xFF = −1

−128+64+32+16+8+4+2+1 = −1

The squares are the same and so is the stored byte. The only thing that changed is which weight we assign to the top square, and that is a decision made by the instruction rather than the memory. The byte itself has no idea whether it is signed.

The whole range

The top square is the sign bit: off means zero-or-positive, on means negative. Nothing above 0x7F is positive when read as signed.

Look at the Unsigned and Signed columns for any row where the top square is lit: the difference is always exactly 256. That is where the implementation shortcut comes from: if bit 7 is set, subtract 256. It is the arithmetic of turning one +128 into a −128, a swing of 256.

Why two's complement and not a plain sign flag? Because addition keeps working untouched. 0xFF + 0x01 overflows to 0x00, and read as signed that is −1 + 1 = 0. Correct, with no special case. The CPU adds the same way whether you meant the bytes as signed or not, which is why the hardware needs no separate signed-add instruction.
07

Wrapping: the odometer

Eight squares cannot count past 255, so they roll over like a car odometer. This is defined, relied-upon behaviour, and the CPU records the roll-over in the carry flag so the next instruction can react.

In Python: u8(0xFF + 1) == 0x00, and the carry is (0xFF + 1) > 0xFF.

It runs backwards too. 0x00 − 1 wraps to 0xFF, and Python's & already does the right thing with negatives: -1 & 0xFF is 255. That is one of the rare places where Python's semantics match the hardware for free.

08

Little-endian: the order on the shelf

Everything above describes a 16-bit value as a single row, left to right. But memory only stores bytes, one per address, so a 16-bit value has to be split across two consecutive addresses, and the Game Boy puts the low byte first.

Writing 0x1234 to address 0xC000

0xC0000x34low byte
0xC0010x12high byte

Reading it back: low = read(0xC000), high = read(0xC001), then join_bytes(high, low) → 0x1234.

The value you write down is 0x1234, high digit first, because that is how humans write numbers. The value in memory is 34 12. Both are correct; they are different views. The bug you will actually hit is reading a byte pair in the order it appears in a hex dump and getting 0x3412.

Where it shows up first. Every instruction that takes a 16-bit operand (JP a16, LD BC,d16, CALL a16) stores that operand little-endian in the ROM, immediately after the opcode. So the fetch is always: opcode, then low byte, then high byte. The stack works the same way.

B · Writing and printing values

# All four literals below are the same integer. Pick by intent:
255
0xFF          # hex: default for registers, opcodes, addresses
0b1111_1111   # binary: when the pattern matters more than the value
0o377         # octal: never useful here

# Underscores are legal anywhere in a numeric literal. Use them:
0b1010_0101   # nibble-grouped, reads like the diagrams above
0xFF44        # the LY register

# Parsing from text (e.g. a .sym file or user input):
int("FF", 16)      → 255
int("0xFF", 0)     → 255   # base 0 honours the prefix
# Formatting. f-strings take a format spec after the colon.
# this is the one piece of syntax worth memorising today.
v = 0xA5

f"{v:02X}"     → 'A5'        # 2 digits, uppercase, zero-padded
f"{v:#04x}"    → '0xa5'      # '#' adds the 0x, width counts it
f"{v:08b}"     → '10100101'  # 8 binary digits
f"{v:3d}"      → '165'       # plain decimal, width 3

# A register dump line, the way you will actually write it:
f"A:{a:02X} F:{f:02X} BC:{bc:04X} PC:{pc:04X}"
               → 'A:A5 F:B0 BC:0013 PC:0100'

# Standalone functions exist too, but give you no padding control:
hex(165)       → '0xa5'
bin(165)       → '0b10100101'
vs. Ruby. Ruby's 255.to_s(2) and "%02X" % v both exist in Python as format() and %, but f-strings have replaced them in modern code. Note 02X is the width including padding, and that # makes 0x count toward that width, so f"{v:#04x}" gives four characters total, of which two are the prefix.

C · Signed conversions, three ways

Turning the byte 0xFF into −1 is “if the top square is lit, subtract 256”. All three of these do exactly that:

# 1. Explicit. Write this one first: it is the diagram in section 06,
#    transcribed. You should be able to derive it from scratch.
def to_signed8(value: int) -> int:
    return value - 0x100 if value & 0x80 else value

to_signed8(0x00)   → 0
to_signed8(0x7F)   → 127
to_signed8(0x80)   → -128
to_signed8(0xFF)   → -1

# 2. Branchless, same result. Clever, harder to read at 2am.
(value ^ 0x80) - 0x80

# 3. Via the bytes machinery. Reads well, allocates a bytes object.
int.from_bytes(bytes([value]), "little", signed=True)   → -1

And the return trip. Going from a Python int that may be negative back to a stored byte needs no branch at all, because Python's & already behaves the way the hardware does:

-1 & 0xFF      → 255   # 0xFF, the byte you would store
-128 & 0xFF    → 128   # 0x80
-1 % 256       → 255   # % agrees; C's % would give -1

# So a relative jump needs no special casing on the way in:
offset = to_signed8(rom[pc + 1])     # 0xFE → -2
pc = (pc + 2 + offset) & 0xFFFF      # wraps correctly either direction
Sixteen bits works identically, with 0x8000 as the sign bit and 0x10000 as the subtrahend. The SM83 has no signed 16-bit operations, so it rarely comes up, but the pattern generalises to any width.

D · Bytes, bytearray, and reading the ROM

A ROM file is bytes (immutable); RAM is bytearray (mutable). Both are sequences of plain ints in 0–255, which means the container enforces the 8-bit range for you on write, but arithmetic still needs its mask.

rom = Path("tetris.gb").read_bytes()   # bytes, immutable
wram = bytearray(0x2000)               # 8 KiB of zeroes, mutable

rom[0x0100]        → 0   # a single index gives an int
rom[0x0100:0x0104] → b'\x00\xc3\x50\x01'  # a slice gives bytes

wram[0x0000] = 0x42          # fine
wram[0x0000] = 0x100         → ValueError: byte must be in range(0, 256)

# Little-endian 16-bit read. Byte order is a parameter, not your problem:
int.from_bytes(rom[addr:addr + 2], "little")     → 0x0150

# ...or spelled out, which is what the CPU actually does:
low, high = rom[addr], rom[addr + 1]
(high << 8) | low
vs. Ruby. This is the biggest day-to-day difference. Ruby's String doubles as a byte buffer and str[0] gives you back a one-character String; Python separates text (str) from bytes entirely, and indexing bytes gives an int. That int is exactly what you want here, with no .ord or .unpack.

E · Four things that will bite you

── 1. ~ returns a negative number ──────────────────────────
~0x08          → -9      # not 0xF7, as C would suggest
~0x08 & 0xFF   → 247     # 0xF7. Always re-mask after ~

It still works unmasked inside an AND (v & ~0x08 is correct),
but the intermediate will confuse you in a debugger. Mask it.
── 2. >> on a negative sign-extends forever ────────────────
-1 >> 4              → -1      # infinite 1s to the left
(-1 & 0xFF) >> 4    → 15      # mask first, then shift

Rule: never shift a value you have not already masked to width.
── 3. Shift binds LOOSER than + and - ──────────────────────
1 << 2 + 3     → 32      # parsed as 1 << 5, not (1 << 2) + 3
(1 << 2) + 3   → 7       # parenthesise, always

The good news, and a genuine difference from C:
& binds TIGHTER than ==, so this needs no parentheses:
v & 0x0F == 5  → parses as (v & 0x0F) == 5, which is what you meant
In C that same line means v & (0x0F == 5). Python fixed it.
── 4. bool is a subclass of int ────────────────────────────
True + True         → 2
isinstance(True, int)  → True

So a get_bit() returning bool can be silently used in arithmetic.
Usually harmless, occasionally the reason a flag ends up as 2.
Ruby's true/false are not Integers; there is no equivalent trap.

When a value ends up somewhere unexpected, draw the row. The bug is almost always a missing mask or a swapped byte order.
